# 录制 → 调查报告 → 写脚本

把"在网站上摸索一遍"变成"一条命令"：

```
bx trace start      录制：bx 的操作、用户手动的操作、所有接口请求和响应体、看到的内容
   … 用 bx 操作，或者让用户自己在浏览器里点一遍 …
bx trace stop       停止，自动整理成调查报告（report.md）
bx script new       根据报告生成脚本骨架（附上报告）
   … AI 读报告、改骨架 …
bx script test      跑一遍，检查输出，和录制时看到的内容对比
```

分工：**程序**做去噪、归纳、溯源这些体力活，**AI** 负责理解意图、写代码，**`script test`** 负责验证。

## 1. 录制

```bash
bx tab open https://www.bilibili.com/v/popular/rank/all
bx trace start rank --goal "B站排行榜：排名、标题、UP主、播放量，支持切换分区"
bx reload                        # 建议先 reload：页面一开始加载的接口也能录到
bx read                          # 拿到数据后 read 一次，报告靠它做"数据溯源"
bx trace mark "切换到动画分区"     # 可选：给关键步骤加标注
bx click e418
bx read
bx trace stop
```

- **`--goal` 一定要写**：它记下了这次摸索的意图，这是程序自己推断不出来的。
- 录制期间用 bx 操作过的标签会**自动加入**录制；点击打开的新标签也会自动加入。用户自己开的标签用 `bx trace add t5` 加进来。
- **用户手动演示也可以**：录制中的标签里，用户的点击、输入、提交、按键、滚动都会被记下来，包括元素的文字和 CSS 选择器。停止录制时会自动抓一次页面文字，当作"看到的内容"。
- 保存位置：`~/.bx/traces/<名字>/`（`trace.json` + `bodies/` + `report.md`）。

## 2. 调查报告

`bx trace digest rank` 可以重新生成并查看报告。报告里有这些内容：

| 部分 | 内容 |
|---|---|
| 结论 | 数据来自哪个接口的哪个字段；有没有签名（给出方案 A/B）；翻页参数；参数要从哪个接口先拿；要不要 cookie / 自定义请求头 |
| 操作时间线 | 每一步做了什么（带元素的选择器），触发了哪些接口 |
| 接口详情 | 参数表（固定 / 翻页 / 时间戳 / 签名 / 来自输入 / 来自前一个接口 / **随操作变化**）、响应结构示意（★ 标出看到的数据所在字段，没用到的部分折叠） |
| 其它 | 其余接口一行一个；被忽略的埋点；在响应里没找到出处的内容 |

背后做了这几件事：

1. **去噪**：图片、字体、CSS、埋点统计、心跳这类请求会去掉。
2. **接口归纳**：同一个路径的请求合并成一个接口（路径里的数字、id 归一成 `{n}` / `{id}`）。
3. **数据溯源**：从 `read`、`snapshot`、`eval` 的输出和页面文字里取出几百条文字，去所有响应体里搜（JSON 按字段搜，HTML 区分是在 `<script>` 里还是在正文里），得到"这条数据来自哪个接口的哪个字段"。
4. **参数溯源**：参数值是你输入的？是页面网址里的？是前面某个接口返回的某个字段？是时间戳或者签名？
5. **操作 ↔ 请求**：每一步操作之后发出了哪些请求。参数值随操作变化时会列出来，比如“点击‘动画’ → rid=1005”。

## 3. 查细节

```bash
bx trace show rank 34 --path data.list[0]    # 看某个请求的完整响应（或其中一部分）
bx trace find rank "风的来信"                 # 在所有响应 / 请求网址 / 请求体里搜一段文字
bx trace list
bx trace rm rank
```

## 4. 生成骨架

```bash
bx script new mysite --from-trace rank          # 放在 ~/.bx/sites/mysite/
bx script new mysite --from-trace rank --project # 放在项目的 .bx/sites/mysite/
```

生成的 `index.js` 会按报告选方案：

- **没有签名的 JSON 接口** → `ctx.tab()` + `tab.fetch()` 直接调；参数表写好了，翻页参数换成变量，来自输入的参数换成命令参数。
- **有签名** → `ctx.open()` + `tab.waitResponse()` 截获页面自己发的请求，并在注释里列出录制时的操作步骤（带选择器），告诉你怎么在页面上触发它。
- **数据在 HTML 里** → 打开页面后用 `tab.eval` 读。

骨架旁边会附上 `TRACE.md`（报告的副本）。骨架通常能直接跑出数据，但命令名、参数、翻页、要输出哪些字段，需要 AI 按报告改好。

## 5. 验证

```bash
bx script test mysite list 关键词 --limit 20 --from-trace rank
```

会检查这些：

- 退出码、输出条数（`--min N`）、是不是每行都是 JSON
- 每个字段有值的比例和示例；**字段全是 undefined**（路径写错了）会报错
- 有没有能给下一个命令用的主键（id / url）
- `--from-trace`：录制时看到的内容，有多少出现在输出里。一条都没对上，通常说明数据来源不对，或者参数和录制时不一样。

失败时退出码是 1，AI 可以根据输出继续修改，直到通过。

## 实例：B 站排行榜

`sites/bili/index.js` 里的 `rank` 命令就是这样写出来的：

1. 录制时，报告指出数据在 `x/web-interface/ranking/v2` 的 `data.list[]`，有 `w_rid` 签名，并且“`rid` 随操作变化：点‘动画’ → 1005，点‘游戏’ → 1008”。
2. 用骨架直接跑（截获方案），5.6 秒能出数据。
3. 因为 B 站的 wbi 签名已经实现过了（`sites/bili/wbi.js`），改成直接调接口，0.3 秒。
4. 用 bx 把每个分区点一遍，从网络记录里读出完整的分区 → rid 对应表。
5. `bx script test bili rank --from-trace rank` 通过。
